# 프로젝트 메모리 저장

이 저장소는 두 종류의 로컬 메모리를 쓴다. 이 스킬은 **메인 세션(나) 자신의 몫**만 담당한다.

| 계층                | 위치                                                      | 관리 주체                                                                                                       |
| ------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 프로젝트 메모리     | `.claude/memory/*.md` + `.claude/memory/MEMORY.md` 인덱스 | **메인 세션(이 스킬)** — CLAUDE.md가 참조하는 팀 공용 지식                                                      |
| 서브에이전트 메모리 | `.claude/agent-memory/<agent>/*.md`                       | 각 서브에이전트가 자기 실행 끝에 스스로 기록 (`code-reviewer`, `supabase-db-architect` 등은 이미 자체적으로 함) |

즉 code-reviewer나 supabase-db-architect를 호출했다면 그 에이전트는 보통 자기
메모리를 알아서 남긴다 — 이 스킬이 그걸 대신 쓰거나 중복 기록하지 않는다. 이 스킬은
**메인 세션이 사용자와 직접 주고받은 대화·직접 수정한 코드·직접 내린 판단**을 놓치지
않고 `.claude/memory/`에 남기는 데 집중한다.

## 1단계 — 기록할 가치가 있는가 판단

작업(또는 대화 턴)이 끝날 때마다 아래 중 하나에 해당하는지 확인한다:

- 버그를 고쳤다 (원인이 코드만 읽어서는 바로 안 보이는 종류)
- 정책/동작을 바꿨다 (예: "승인된 상품 수정은 재검수 생략") — 나중에 "왜 이렇게
  동작하지?"를 코드만 보고는 알 수 없는 결정
- 비직관적인 제약/함정을 발견했다 (예: select_columns 화이트리스트를 안 갱신하면
  컬럼 추가해도 API에 안 나타남)
- 사용자가 접근 방식을 정정했거나("그렇게 하지 마") 반대로 승인했다("그 방식 맞아,
  계속 그렇게 해")
- 미완료로 남긴 일이 있다 (예: 마이그레이션 SQL은 작성만 하고 아직 미실행,
  후속 조치가 필요한 Minor 지적 사항)
- 새로운 아키텍처 컨벤션이나 관례가 이번에 처음 확정됐다

**해당 없음 → 아무것도 쓰지 않는다.** 아래는 저장하지 않는다:

- 코드/git log/git blame으로 바로 파악 가능한 것 (구조, 최근 변경 이력)
- CLAUDE.md나 기존 `.claude/memory/*.md`에 이미 있는 내용
- 이번 세션에서만 의미 있는 일시적 상태(진행 중 작업, TaskCreate로 이미 추적 중인 것)
- 비밀값(API 키, 토큰, 비밀번호) — 절대 파일에 쓰지 않는다

## 2단계 — 기존 메모리와 중복인지 확인

새 파일을 만들기 전에 `.claude/memory/MEMORY.md`를 훑고, 관련 키워드로
`grep -ril <키워드> .claude/memory/`를 돌려 이미 다루는 파일이 있는지 확인한다.

- **있음** → 그 파일을 Edit로 갱신한다(날짜와 함께 새 절 추가, 기존 결정을 뒤집는
  경우 뒤집힌 이유를 명시). 새 파일을 또 만들지 않는다.
- **없음** → 3단계로 새 파일을 만든다.

## 3단계 — 새 메모리 파일 작성

`.claude/memory/<snake_case_slug>.md`로 저장한다. 파일명은 `name:` 필드와 동일해야
한다. 이 저장소의 다수 관례(전체 25개 파일 중 19개, 76%)를 따른다 — **플랫 `type:`
필드**를 쓰고, 시스템 레벨 auto-memory의 `metadata: {type: ...}` 중첩 형식은 쓰지
않는다. (참고: 25개 중 5개는 아직 `metadata:` 중첩 형식이고 1개(`cors-setup.md`)는
프런트매터 자체가 없다 — 기존 드리프트이며 신규 작성 시 따라가지 말 것. 이 파일들을
직접 수정할 일이 생기면 플랫 `type:`으로 정리해도 된다.)

```markdown
---
name: <slug, 파일명과 동일>
description: <한 줄 요약 — 나중에 관련성 판단에 쓰이므로 구체적으로>
type: project | feedback | reference
---

<본문. project/feedback 타입은 다음 구조를 따른다:
사실/결정 한 줄 → **Why:** (배경, 사용자가 준 이유, 발견 경위) → **How to apply:**
(다음에 이 주제를 마주치면 어떻게 판단해야 하는지). 관련 메모리는 [[다른-slug]]로
링크한다.>
```

`type` 선택 기준 (이 저장소에서 실제 쓰이는 값):

- **project** — 무슨 일이 있었는지, 왜, 현재 상태(완료/대기 중). 가장 흔한 타입.
- **feedback** — 사용자가 준 접근 방식 지침(하지 말 것 / 계속할 것)
- **reference** — 외부 시스템 포인터(Linear, Slack 채널 등)

## 4단계 — `.claude/memory/MEMORY.md` 인덱스 갱신

새 파일이면 한 줄을 추가하고, 기존 파일을 갱신했다면 해당 줄의 요약을 최신 상태로
고친다. 기존 스타일 그대로:

```markdown
- [제목](파일명.md) — 한 줄 요약(무엇을, 왜, 현재 상태)
```

`MEMORY.md`는 인덱스일 뿐이다 — 내용을 여기 직접 쓰지 않는다.

## 5단계 — CLAUDE.md는 건드리지 않는다 (예외적 경우만)

CLAUDE.md의 "빠른 참조" 표는 사람이 큐레이션한 목록이다. 이번에 확정된 내용이
**새로운 절대 규칙** 수준이 아니라면 CLAUDE.md는 수정하지 않는다. 절대 규칙 추가가
필요해 보이면 먼저 사용자에게 확인한다.

## 출력 형식

메모리를 썼다면 사용자에게 보고할 필요 없이 조용히 반영하고, 다음 형태로 마음속
체크만 한다(대화에 노출할 필요는 없음, 단 사용자가 "메모리 저장했어?"라고 물으면
아래로 답한다):

```
[대상]     상품 수정 시 재검수 스킵 정책
[유형]     project
[저장 위치] .claude/memory/product_license_approved_edit_no_reverify.md (신규)
[인덱스]   MEMORY.md 갱신 완료
```

기록할 가치가 없다고 판단했다면 그냥 아무것도 하지 않는다 — 매 턴 빈 메모리를
만들 필요는 없다.
